# #41 — queries v1: parameterized rules and in-rule invocation

Queries are the first DRLX feature that touches every layer of the pipeline — grammar, IR, visitor, and runtime builder — while also requiring a new drools runtime object type. I wanted to understand the risk before committing, so the session started with a feasibility check.

## Scoping: what to ship, what to defer

The DRLXXXX spec describes queries as "rules with parameters" — a unification of the old DRL `query ... end` block with the regular rule syntax. The full spec covers recursive transitive closures, `@Tabled` memoization, passive invocation, result binding, named access. I asked Claude to survey the drools codebase for the query infrastructure.

Claude came back with a thorough map: `QueryImpl` extends `RuleImpl`, `QueryElement` and `QueryArgument` handle in-rule invocation, `PhreakQueryNode` manages the rete propagation — all in `drools-base` and `drools-core`, already on the DRLX classpath. No drools-side changes needed.

We scoped v1 to two capabilities: query definition (compile a parameterized rule as `QueryImpl`) and basic invocation from other rules (compile a query call as `QueryElement` with positional arguments). Recursive queries, `@Tabled`, and named access become follow-up issues.

## The prefix pattern: how drools wires query parameters

The core mechanism is what drools calls a "prefix pattern." When a query is defined, the compiler prepends a synthetic `Pattern` to the LHS that matches `DroolsQuery` objects. This pattern carries a `QueryNameConstraint` (matches by query name) and `ArrayElementReader` declarations (extract each parameter from the `DroolsQuery.elements[]` array). The result: query parameters become ordinary bound variables available to the rest of the LHS.

Drools' `PatternBuilderForQuery` creates the field readers via `ClassFieldAccessorStore` in `drools-mvel`, which isn't on the DRLX classpath. We needed a lightweight replacement — a custom `ReadAccessor` that calls `DroolsQuery.getElements()` directly:

```java
public final class DroolsQueryElementsReader implements ReadAccessor {
    public static final DroolsQueryElementsReader INSTANCE = new DroolsQueryElementsReader();

    @Override
    public Object getValue(ValueResolver valueResolver, Object object) {
        return ((DroolsQuery) object).getElements();
    }
    // ... remaining ReadAccessor methods
}
```

## The beta constraint bug that `var` exposed

The first runtime test — `executeQuery("PersonsByAge", 25, Variable.v)` — threw `DroolsQueryImpl cannot be cast to Integer`. The symptom pointed at the `ArrayElementReader`, but the actual bug was in `DrlxLambdaBetaConstraint.buildEvalMap()`. It extracted bound variable values via `fh.getObject()` — the raw fact from the tuple — instead of going through the declaration's `ReadAccessor` chain. For regular pattern bindings where the accessor is `SelfReferenceClassFieldReader`, both paths return the same thing. But for query parameters backed by `ArrayElementReader`, `fh.getObject()` returns the `DroolsQueryImpl` object while `decl.getValue()` extracts `elements[0]` — the actual integer `25`.

The fix: `decl.getValue(null, fh.getObject())` instead of `fh.getObject()`.

## Two-pass compilation and scope isolation

Query invocation requires the target `QueryImpl` to exist before the calling rule is compiled. The builder's single `forEach` over rules became a two-pass loop: pass 1 compiles all parameterized rules into `QueryImpl` objects and registers them by entry point name; pass 2 compiles regular rules, checking the registry when a `PatternIR` entry point matches a known query.

The grammar change that enabled bare OOPath at the rule-item level — `/personsByAge(25, var p),` — exposed a pre-existing scoping bug: `buildLhs()` shared `boundVariables` mutably across group elements, so bindings inside `or()` leaked to subsequent patterns. The fix: pass a defensive copy of `boundVariables` when building `OR`, `NOT`, or `EXISTS` children.
